01 A clearly defined user

The reviewer of a data pipeline change who has to say BLOCK or PASS.

A data engineer, or the human behind a coding agent, looking at a small diff in a transformation pipeline minutes before it ships.

What that person needs

  • Which tables and dashboards this diff reaches, not just which functions.
  • How much the output moves on the same input, row by row and in aggregate.
  • What the code was supposed to guarantee, next to the evidence that it no longer does.
  • Something they can re-query themselves rather than trust a tool's summary.
Secondary stakeholder
Finance, the consumer of the "Daily Revenue dashboard" and the "month-end close extract". They never see the diff, only its consequences.

03 A focused solution

One command. Seven steps. One review card.

1 · GRAPH
entire graph diff
base..head → changed symbols, e.g. normalize_amount
2 · GRAPH
entire graph impact
callers and data flows → pipeline entry points
3 · CONFIGURED
ripple.toml mapping
entry point → Databricks job, input and output tables, data products
4 · CHECKPOINT
Intent lookup
INTENT.md plus entire checkpoint for the affected pipeline
5 · EXECUTE
Run base and head
both versions over the same input snapshot
6 · DATABRICKS
Compare in SQL
row-level and aggregate diff on the warehouse, tagged with a run_id
7 · CARD
Review card
intent, source lines, data products, reproducible comparison, verdict

Scope chosen for the event window

  • One Python pipeline, three Delta tables, one aggregate: daily net revenue.
  • One seeded regression: abs() introduced while "normalizing amounts".
  • Source-to-job mapping is configured, not discovered, and labelled as such on the card.

Why Entire is essential

  • Without the graph, Ripple would re-run every pipeline on every change.
  • Without checkpoints, the card could show a delta but not the requirement it violates.
  • Graph output is treated as evidence, not an oracle. Every relation carries a confidence label.

03 How a change ripples outward

Graph edges reach the entry point. Configuration reaches the data.

The two inner rings come from entire graph impact and are labelled [CALLS, entire-graph] with their call-site line. The two outer rings come from ripple.toml and are labelled source = configured. The card never blurs the two.

Then the decisive step: execute both versions over the same 150-row snapshot and let Databricks compute the difference.

04 Noon Curveball: the graph is evidence, not an oracle

Zero callers and "completeness: ok" can both be true while the graph is wrong.

We rerouted the same pipeline through a string registry and globals(). The real graph output: 0 callers, completeness ok, no partial failures. The MVP would have returned PASS without executing anything. The graph does not know what it missed, so its own signals cannot flag it.

tests/fixtures/transactions_dynamic_dispatch.py
STEP_REGISTRY = {"normalize": "normalize_amount", ...}
fn = globals()[STEP_REGISTRY[step]]
PARTIAL ANALYSIS. The call graph may be missing callers of the changed code. Graph relationships are labelled per edge; nothing here is PASS on graph evidence alone.
· dynamic reference at transactions.py:13 (symbol name as string literal)
· dynamic reference at transactions.py:26 (reflection via globals())
· Fallback: executed pipeline.transactions:run even though the graph did not reach it.
Evidence: analysis partial; 2 confirmed, 0 heuristic, 2 needs-verification

What changed, smallest complete revision

  • Tri-state label on every edge: confirmed structural CALLS with call site · heuristic data-flow, co-change, or a degraded graph run · needs-verification no call site, or a path only Ripple's scan sees.
  • Partial detection from two sources: the graph's own warnings and completeness fields, plus a Ripple-side AST scan for a symbol name used as a string constant in a file that also uses reflection.
  • Safe fallback = execute anyway. Configured entry points the graph did not reach are run and compared. Execute-and-compare is the verification path.
  • New verdict: NEEDS-VERIFICATION, exit 3, when analysis is partial and nothing was executed. PASS on graph evidence alone is impossible in the partial state.

04 Best Use of Databricks

The BLOCK decision is a SQL result a reviewer can re-run.

What runs where

  • Snapshot and both outputs land in Unity Catalog Delta tables under workspace.ripple, tagged with a run_id.
  • Row-level diff, aggregate diff and totals are computed on the serverless SQL warehouse through the Statement Execution API.
  • The three statement ids and the SQL are printed on the card and saved to evidence/databricks/last_run.json.
-- daily_revenue, base vs head, same run_id
SELECT b.txn_date,
       b.net_revenue AS base,
       h.net_revenue AS head,
       h.net_revenue - b.net_revenue AS delta
FROM   workspace.ripple.daily_revenue b
JOIN   workspace.ripple.daily_revenue h
  ON   b.txn_date = h.txn_date
WHERE  b.run_id = '<run_id>' AND b.version = 'base'
  AND  h.run_id = '<run_id>' AND h.version = 'head'
  AND  b.net_revenue <> h.net_revenue;

-- 2026-08-12:  -135.29 → 135.29  (delta 270.58)

Honest scope

  • The two Python versions execute locally from git revisions. Databricks stores and compares. Running the pipeline as a Databricks job is the next step.
  • Free Edition, one 2X-Small warehouse, about 1 minute cold start. Whole review about 70 s.
  • Inserts use literal VALUES: fine for 150 rows, not for millions.
  • If the CLI or warehouse fails, the card falls back to the local comparison and says so.

06 A practical continuation path

Known limits today, and the next concrete step for each.

Limitation nowNext step
Dynamic-reference scan is Python-only and same-file: a name in YAML dispatched from another module is not caught (the graph-signal path still applies).Scan configured entry files for string constants naming any changed symbol across files; add a CONFIGURES-edge check.
entire graph indexes the working tree, so impact for a head revision that is not checked out reflects the checked-out code. The demo uses a worktree.Run the impact query inside a temporary worktree at head automatically.
Both pipeline versions execute locally. Databricks stores and compares.Run the pipeline as a Databricks job so the fallback executes there too, and batch inserts for large snapshots.
Entry point → data product mappings are hand-configured in ripple.toml.Read Unity Catalog lineage to discover them, and label those edges with their own evidence level.
One pipeline, one aggregate, one warehouse.Multi-pipeline repos, a CI gate on the exit code, and the card posted as a PR comment.

What it takes to become a reliable product: automatic worktree indexing, job-based execution on Databricks, lineage-driven mappings, and a CI integration. Each is a bounded change to one module of a 1,000-line package.
