Ripple connects code changes to downstream data consequences.

A data engineer changes a transformation. The code looks reasonable, but a downstream report silently changes meaning.

Ripple combines three inputs:

Entire Checkpoints explain the intended behavior.
Entire Graph identifies the changed function and related code.
Databricks executes a comparison of the old and new transformations against the same input snapshot.

The demo: A checkpoint says refunds must remain negative. An agent introduces abs(amount) while “normalizing transaction amounts.” Ripple traces the changed helper to the transaction pipeline, executes both versions, and shows precisely which rows and revenue aggregates differ.

The result is a review card containing the original requirement, source locations, affected data products, and a reproducible comparison.

Why both platforms matter: Entire supplies intent and code relationships. Databricks supplies the data execution and downstream evidence needed to quantify the consequence.

For a stronger version, incorporate Unity Catalog lineage to discover downstream tables and dashboards. Databricks exposes queryable lineage system tables, though access must be enabled and lineage coverage is incomplete. Databricks lineage documentation

Scope the MVP: One Python pipeline, three Delta tables, one aggregate, and one seeded regression. Start with an explicit, inspectable mapping between a source entry point and its Databricks job. Automatic mapping discovery can wait.

The main implementation risk: Joining code relationships to data lineage. Validate that connection early, and label configured mappings separately from discovered relationships.
